# Phase 9, Task 0 — Can the helper take only the sound tagged as music?

**Date:** 2026-11-05
**Question** (owner, 2026-10-26; solution review OV-06): could Music's spectrum follow only the sound that players tag as music, instead of everything the PC plays on its default output?
**Answer:** technically yes, without a native PipeWire library, but few players tag their sound as music. Of six common players, only Spotify did. Browsers, VLC by default and mpv by default don't, so a music-only capture would show silence for most music played in a browser.

## Method

- **Tags, measured:** each installed player played a sound while `pw-dump` listed the playback streams and their properties. mpv and Chrome played a test tone into a temporary virtual output (`pactl load-module module-null-sink`), so nothing was heard; it was removed afterwards. The owner played a song in Spotify on the normal output.
  - mpv: a 440 Hz sine generated by its `lavfi` input, audio only.
  - Chrome: a page playing a Web Audio oscillator, in headless mode with a throwaway profile, the owner's own profile untouched.
- **Tags, from source:** VLC, Firefox and Chromium aren't installed on this PC and weren't installed for this task (owner, 2026-11-05). Their source code answers instead, marked as not measured. mpv's source was read too, to explain its measurement.
- **Capture limited to tagged streams:** a throwaway experiment in the session scratchpad, never committed (below).

## Which players tag their sound as music

PipeWire's `media.role` property names a stream's purpose ("Music", "Movie", "Communication", …). A PulseAudio client sets the same through `PA_PROP_MEDIA_ROLE`, which PipeWire's PulseAudio server passes on.

| Player | `media.role` | How it's known |
|---|---|---|
| Spotify | **Music** | Measured, playing a song |
| mpv | none | Measured, audio only. Its PipeWire output sets Music or Movie only when its `set_media_role` option is on, which is off by default (`audio/out/ao_pipewire.c`) |
| Chrome | none | Measured, Web Audio in a page. Chromium's PulseAudio code sets only the application's icon name on a playback stream (`media/audio/pulse/pulse_util.cc`) |
| Chromium | none | Not measured: the same code as Chrome |
| VLC | **Video** by default | Not measured: its PipeWire and PulseAudio outputs set the role from VLC's `role` option (`modules/audio_output/pipewire.c`, `pulse.c`), whose default is `video` (`src/libvlc-module.c`), whatever the file plays |
| Firefox | none | Not measured: neither of Firefox's audio backends for PulseAudio, cubeb's C one (`src/cubeb_pulse.c`) or its Rust one (`cubeb-pulse-rs`, `src/backend/stream.rs` and `context.rs`), sets a role |

So music played in a browser (web players, video sites), in mpv by default, or in VLC by default isn't tagged as music.

## Capturing only the tagged streams

- Two mpv instances played into the virtual output: a 440 Hz tone tagged Music (through PipeWire's `PIPEWIRE_PROPS` environment variable) and a 1 kHz tone with no role.
- `pw-record` ran with `node.autoconnect` off, so PipeWire linked it to nothing, and `pw-link` linked the tagged stream's two output ports to its two input ports.
- In the recording, the 440 Hz tone's amplitude was 0.088, and the 1 kHz tone's was exactly 0.

So the helper could capture only tagged streams with PipeWire's own tools: it would watch the streams as they come and go (`pw-dump --monitor` prints every change as JSON), and link each tagged one's output ports to its capture with `pw-link`. No native binding, so no libclang at build time. The capture would follow a tagged stream whatever output it plays on.

## Open points if the source changed

- **The delay** (150 ms for 95 % of frames) wasn't measured. A direct link from a stream to the capture adds no buffer beyond the capture's own 20 ms latency, the same as the output's monitor does, so it should hold; this is unverified.
- **When nothing tagged plays**, the spectrum would be silent, or it could fall back to the default output's monitor. That's a product choice.
- **The helper grows:** it would follow streams appearing, disappearing and changing tags, link and unlink their ports, and handle mono and multichannel streams, where the planned helper only starts `pw-record` on the monitor.

## How DeepCreative does it on Windows

Read from DeepCreative 1.2.14's .NET helper by static analysis, without running it (2026-11-05):
- it creates NAudio's `WasapiLoopbackCapture` with no arguments, which takes Windows' default playback device for multimedia (`GetDefaultAudioEndpoint`, render and multimedia role) and opens it in loopback mode: everything played on that device, with no filter by application;
- it reads the default device again on a timer and restarts the capture when the default output changes;
- it reads 16-bit samples and runs its own FFT, which OpenDeepCool doesn't copy (`music.md`).

So the planned source, the default output's monitor, is what DeepCreative does. On Linux, WirePlumber moves the monitor's capture to a new default output without code.

## Recommendation

Keep the default output's monitor, as planned. Music-only would leave the spectrum flat for most of the music people play on a PC, in a browser, and for VLC and mpv as they come. If the owner wants the music-only behaviour anyway, the fallback form is the safer one: tagged streams while any plays, the default output otherwise.

## Decision

The owner keeps the default output's monitor, as DeepCreative does (2026-11-05). `music.md` (Source) and the PRD (Open Questions; Decisions Log: Audio source) record it.
