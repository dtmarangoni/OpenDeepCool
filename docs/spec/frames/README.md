# Expected frames

The frame OpenDeepCool must send to the LP360 for every case of the test matrix: every mode × the four rotations × °C and °F where a temperature is shown, with three value sets per case. The Rust tests compare their output with these files (PRD, Testing Strategy).

They're drawn from the spec's rules alone ([display.md](../display.md), [music.md](../music.md)): OpenDeepCool's rules, which differ from DeepCreative's on purpose in a few places (owner decisions of 2026-10-24, and the rounding of 2026-10-26):
- every value in full up to 9999, never cut to DeepCreative's 99 or its last two digits; 10 000 and more are drawn `9999` (owner, 2026-10-25), which no case here reaches;
- static while every value is 99 or less, scrolling while one is 100 or more, °F and power included;
- one value centred, two values ending at column 14;
- where DeepCreative shows the wrong metric, the metric the mode names (AGENTS.md rule 11), for example the CPU Temperature in mode 18 in °F;
- every measurement rounded to the nearest whole number, halves up, and °F rounded once from the exact °C reading.

Where the two sets of rules agree (for example two-digit usage, or two-digit °C in one band), the same cases reproduce DeepCreative's captured frames pixel for pixel. Regenerated on 2026-10-24 with these rules: 172 of the 292 cases changed.

**Regenerated again on 2026-10-26** for the nearest rule (owner, `display.md` Values): 24 of the 284 cases changed, all in °F.
- 57 °C now draws `135°F` and 7 °C draws `45°F`, where DeepCreative's rule gives `134°F` and `44°F`.
- They're in modes 7 and 18 (CPU Temperature 57), modes 8 and 19 (Gpu temperature 7), and mode 9 (both), each in all four rotations.
- The other 260 cases are unchanged, byte for byte: every other reading is a whole number, and its °F conversion rounds the same either way.

**Titles, 2026-10-28:** each file's first line names the mode as the settings app does, `<group> · <option>`, for example `# Mode 4: Load · CPU + GPU` instead of DeepCreative's "Load Mode, Combined, CPU / GPU" (owner; [design](../../design/settings-app.md)). No picture changed.

## Format

One file per mode, `mode-NNN.txt`. Each `##` section is one case:

- **Heading:** the rotation value (0–3, see [rotation](../display.md#rotation)), the unit where it matters, and the readings of the metrics the mode shows. Every metric has its own distinct value in each value set. Mode 23's headings name the Dancer's pose instead, `pose 0` to `pose 10`.
- **Frames:** 14 rows of 14 characters, row 1 at the top, as the cooler shows them:
  - `#` on, `.` off;
  - `?` a spectrum pixel: it depends on the sound, so it's checked by the spectrum's layout rules instead (solid bars from the floor, at most one peak dot above each, height limits).
- **Static case:** one frame, sent unchanged while the readings stay the same.
- **Scrolling case:** one cycle in time order, one frame per 100 ms tick, seven per line: 21 frames, or more when the text is wider than 17 columns. The first frame is the home position, which is what the display shows on the first frame after a mode switch; after the last frame the cycle starts again.
- **Emoji case:** one loop of pictures in order, with their durations above them.

## Readings used

| Value set | CPU Usage | Gpu usage | Memory Load | CPU Temperature | Gpu temperature | CPU Power | Gpu power |
|---|---|---|---|---|---|---|---|
| 1 | 3 | 6 | 8 | 4 | 7 | 5 | 9 |
| 2 | 42 | 67 | 85 | 57 | 38 | 65 | 250 |
| 3 | 100 | 91 | 77 | 120 | 93 | 1234 | 999 |

The files are generated from the spec's rules by `tools/oracle/` (`odc-oracle`), a Rust program that shares no code with OpenDeepCool (owner, 2026-10-27 and 2026-10-28):
- `cargo run -p odc-oracle -- docs/spec/frames` rebuilds them;
- `cargo test -p odc-oracle` fails when a committed file differs from what the oracle draws.

The oracle is a port of the research script that drew the files first, and draws the same files byte for byte. If a rule in the spec changes, the oracle and the files change in the same commit. Where OpenDeepCool's rules agree with DeepCreative's, the layer 2 tests still compare the renderer with DeepCreative's captures (PRD, Testing Strategy).

## Dash cases and scenarios

More files, generated by the same oracle from the same rules (Phase 7 plan, Task 1; Phase 8 plan, Task 1; Phase 9 plan, Task 1):

- **`unavailable.txt`:** the dash cases of [Unavailable values](../display.md#unavailable-values), in the format above. Each heading starts with the mode, `## mode 4, rotation 0, …`, then the unit where the mode shows a temperature, and a reading may be `unavailable` or negative. Each case in rotations 0–3:
  - mode 1 with CPU Usage unavailable, and at −5;
  - mode 4 with CPU Usage at 42 and at 100 (scrolling), Gpu usage unavailable;
  - mode 6 with both unavailable;
  - mode 7 with CPU Temperature unavailable, in °C and in °F (`--°C`, `--°F`);
  - mode 9 in °F with CPU Temperature at 120 (`248°F`, scrolling) and Gpu temperature unavailable;
  - mode 10 with CPU Power unavailable (`--W`), as in its first second;
  - mode 11 with Gpu power at −3;
  - mode 12 with CPU Power at 1234 (scrolling) and Gpu power unavailable.
- **`scenarios/`:** every [test scenario](../display.md#test-scenarios-opendeepcool) (S1–S26, and S15b) that applies, for every mode from 1 to 23, in rotation 0, run through [Movement, precisely](../display.md#movement-precisely), and in Music modes through `music.md`'s spectrum, emoji loops and Dancer. The rotations 1–3 aren't written: their frames are these, turned.
  - **One file per mode,** `mode-001.txt` to `mode-023.txt`, named like the frame files, holding every scenario that starts in that mode. A Music mode's file also holds the switches into it from modes 1–12, so the files of modes 1–12 stay as Phase 8 wrote them. Each stays under the commit guard's 2 MiB limit (owner, 2026-11-05).
  - Modes 7–9, 18 and 19 run each scenario in °C and again in °F, except the two that need a one-digit value, which no reading draws in °F (0 °C is 32 °F): S2 from one digit, and S9.
  - **Heading:** `## <scenario> · mode <N>`, then details separated by ` · `: the unit (`°C` or `°F`) where it matters, in two-value modes the value a change applies to (`top`, `bottom` or `both`), the case, and `k <n>`, how many columns the strip has moved past home when the change comes. In a Music mode without values, `at tick <t>` names the tick the change comes at instead: each tick of a burst's period in mode 13, each position of the emoji loop in modes 14–17, ticks 1 to 10 of the beat train in mode 23.
  - **Ticks:** one line per tick from 0, `<tick>: <changes> → <frame>`. The changes are `-` or a list separated by `; `:
    - `reset <cause>`: `start-up`, `mode <N>`, `rotation +<d>` (d quarter turns added), `unit celsius` or `unit fahrenheit` (a unit change in a mode that shows a temperature), `another GPU` or `Refresh`;
    - `unit celsius` or `unit fahrenheit`, at tick 0 only: the unit the scenario starts in. It's named where a mode the scenario shows has a temperature, and a scenario that names none runs in °C;
    - `<metric> = <reading>`: an exact decimal, negative ones included, or `unavailable`. Tick 0 gives all seven metrics of modes 1–12, the ones a mode doesn't show included, so a switch into another kind of mode draws named readings. Temperatures are in °C, whatever the unit drawn;
    - `unit celsius, only saved`, `unit fahrenheit, only saved` (a unit change in a mode without a temperature), `already set: <setting>` and `refused: mode <N>, <reason>`: nothing changes on the cooler. A unit only saved is the one the next mode with a temperature draws;
    - `cooler away` and `cooler back`: while it's away, the frames are drawn but don't reach it, and `03 08` comes before the frame of the tick it's back;
    - `wake`: back from standby, `03 08` comes before that tick's frame;
    - `missed`: the tick's deadline is missed, so there's no frame and the strip doesn't move. It comes only in silence;
    - `audio <signal>`: the signal of `spectrum/signals.txt` with that name plays from this tick, so the window of tick *n* is the signal's tick *n* − *t*; before and after it, silence. A scenario without one is silent;
    - `music peaks on` or `off`, `music bar fall <stop>` and `music peak fall <stop>`, a stop being `slower`, `slow`, `moderate`, `fast` or `faster`: a Music setting (S15b), never a reset. The spectrum shows it on that tick's frame; in a mode without a spectrum it's only saved. A scenario starts with the defaults: peaks on, bars moderate, peaks slow.
  - On one tick the readings change first, then a reset applies, so a reset draws the new readings at home (S21).
  - **Music modes** (Phase 9 plan, Task 1):
    - the spectrum's levels start at 0 when a mode from 13 to 22 is entered from any other mode, 23 included, and carry on between modes 13–22 and across every other reset (`music.md` point 8);
    - a reset restarts the emoji loop, and the Dancer, which then runs that tick's rules;
    - modes 18–22 run every scenario S1–S26 that applies, in silence, as modes 1–12 do, so the spectrum is the floor line;
    - modes 13–17 and 23 run S14 into every other mode, S16, S25 and S26 at every position, S15 (a unit change, only saved), S17 in silence and with sound, and S18, while their sound plays: the burst train in 13–17, the beat train rising 0.13 a tick in 23;
    - every switch from a Music mode into another Music mode plays the burst train, or the beat train into 23, and every switch into a Music mode from modes 1–12 plays it from tick 0;
    - every mode from 13 to 22 runs S15b with each stop, and the files of modes 13 and 23 add a Music setting changed in mode 1 and in mode 23, only saved, then drawn in mode 13.
  - **Mode switches (S14):** from each mode into every other mode from 1 to 23, so all 506 ordered pairs, a switch into or out of a mode with a temperature in both units. From a mode with values, at every *k* while it scrolls, with values below 100, above it, and only the CPU's above it, the last left out where the mode switched into shows no values; from a Music mode without values, at every position, with the three sets where the mode switched into shows values.
  - **Frames:** `f<n>` names a frame written once under `# Frames` of the same file, as `### f<n>` and 14 rows; a missed tick has `no frame`.
  - **History:** the Load scenarios were first one file, `load.txt`: 2,499 scenarios and 3,473 distinct frames, generated on 2026-10-29. On 2026-11-05 they moved to the files of modes 1–6, tick 0 gained the other metrics, the switches into modes 7–12 came in, and the "not yet available" example moved from mode 9 to mode 13. The 2,499 earlier scenarios draw the same frames as before. Later the same day S23's refused example became mode 24, outside the mode table, since Phase 9 draws every mode (owner).
  - **Counts, 2026-11-05:** modes 1–12, 10,403 scenarios in 7.5 MB, mode 9's file the largest: 1,826 scenarios, 2,349 frames, 1.47 MB. Modes 13–23, 15,054 scenarios in 9.3 MB, mode 18's file the largest: 2,765 scenarios, 1,411 frames, 1.72 MB.

## The spectrum

Three files, generated by the same oracle from `music.md`, "OpenDeepCool's spectrum, precisely" and "Dancer" (Phase 9 plan, Task 1). The oracle has its own radix-2 FFT and shares no code with OpenDeepCool.

- **`spectrum/signals.txt`:** 89 test signals as text, so the Rust tests make the same samples:
  - for the spectrum, 81: silence; a tone at each column's centre at −20, −45 and −70 dBFS; a tone 2 % below and above each band edge; two tones in two columns; a burst train (100 ms on, 400 ms off) for the bars' and peaks' fall; a sweep of stepped tones from 40 Hz to 16 kHz; white noise from a generator the file states;
  - for the Dancer, 8 beat trains, named `beat train, …`, last: a 60 Hz tone (column 1, whose *bass* is column 2's level) at *bass* levels 0.02 above and below the 0.35 beat and the 0.6 big move, rises of 0.13 and 0.11 around the 0.12 a beat needs, a staircase of rises a tick apart, and a steady tone. Each tone's dBFS is set to 0.1 dB for its *bass* level, and lasts 28 ticks or more.
  - Each signal is a list of segments, `silence <ticks>`, `tones <ticks>: <f> Hz <dB> dBFS, …` or `noise <ticks>: <dB> dBFS`, after a `moved <dB>` line: the oracle moves a signal by 0.5 dB steps until no value it draws lies within 10⁻⁶ of a rounding boundary or of one of the Dancer's thresholds, so the two FFTs' last bits never decide a pixel or a pose. None had to move on 2026-11-05.
- **`spectrum/expected.txt`:** for each signal but the beat trains, *H* 12 and 6, peaks off with each bar fall stop, and peaks on with each bar and peak fall stop (60 sections a signal, 4,860 in all): every tick's 14 bar heights, and with peaks on the 14 dot heights, `.` where no dot is drawn. Heights are `1`–`9`, then `a`, `b`, `c`. The spectrum enters at level 0 at tick 0. 1.5 MB, generated on 2026-11-05.
- **`spectrum/dancer.txt`:** for each of the 89 signals, the Dancer's pose at every tick, `0` to `10` separated by spaces, from a reset at tick 0. Each beat train comes again with ` · resets at ticks 7 and 19` added to its heading: the Dancer also resets before those ticks. 97 sequences, generated on 2026-11-05.
- **`mode-023.txt`:** each of the Dancer's eleven poses, read from `music.md`'s pictures, in rotations 0–3: 44 cases headed `## rotation <r>, pose <k>`. Pose 0, standing still, is what silence shows; `dancer.txt` says which pose each tick shows (owner, 2026-11-05).

A stopped picture is always at home: when its width changes, one value is re-centred and two values keep ending at column 14 (owner, 2026-10-29; S9).
