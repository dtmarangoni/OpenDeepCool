What changes

Approach
  • A new crate, odc-app, builds the binary opendeepcool (gtk4-rs, plain GTK4), in three layers:
    • a pure view model turns the service's state into what each screen shows;
    • a pure theme module turns colors.toml and shell.toml into one CSS string;
    • a thin GTK layer builds the design's widgets.
  • The service gains the five additions the design needs:
    1. the current frame as a signal addressed to each watcher, while watched;
    2. the RPM per fan input;
    3. GPU IDs and a rule flag;
    4. the GPU in use;
    5. whether each saved input is present. There's no CanChangeSettings() (owner, 2026-10-26): only the active local session can use the service, so a refused GetState() tells the app it's in another session.
  • Tests, in the PRD's layers:
    • layer 1: the view model and the theme, pure Rust;
    • layer 3: the app's widgets in-process, in headless weston, against fakes;
    • layer 4: the real app driven through AT-SPI in headless weston, against a fake service everywhere and against the real dev service on the owner's PC.
    • Layer 2 (differential against DeepCreative) has nothing to compare: OpenDeepCool's app has its own design.

Acceptance

AC1 — Everything reachable: every row of the design's coverage check is reached through the real app in layer 4, with the exact D-Bus call logged by the fake, and each tile maps to exactly one mode (Tasks 3, 5, 6, 8).

AC2 — Instant apply, the service's word: a control shows its new state only after the service confirms it; a refused change leaves the old state; a remote or inactive session shows only the not-available state and sends nothing (Tasks 3, 8).

AC3 — The preview is the cooler: the preview draws exactly the frames the service writes, in every rotation, scrolling, Music and the Dancer included. With no watcher the service sends no frames, and frames reach only authorized watchers, never broadcast (Tasks 2, 4, 9).

AC4 — Every state as designed: each row of the design's States table shows its banners, captions, reason lines, insensitive controls and labels, in unit tests and through AT-SPI (Tasks 3, 4, 8).

AC5 — Theme:

  • the Omarchy theme's colours apply and follow an omarchy-theme-set-style folder move within a second, keeping the page;
  • with no Omarchy theme the default dark theme applies; a missing key falls back alone and is logged;
  • no window opacity is ever set (Tasks 3, 7, 8).

AC6 — Contract additions: WatchFrames/Frame, the RPM in FanInputs, the Gpus IDs and rule flag, GpuInUse and the present flags behave as Task 2 specifies, frames go to authorized watchers alone, and docs/spec/dbus.md and settings.md list them (Task 2).

AC7 — Accessible and keyboard-usable: every name in the design's table is set; focus never applies a tile; the shortcuts work (Tasks 4–6, 8).

AC8 — Real system, unattended: on the owner's PC the real app changes the real dev service's frames, unattended and invisible (headless), and leaves the owner's settings as found. The launcher entry opens the app (Task 9).

AC9 — Records: AGENTS.md, README, the PRD footprint, the design document's answered points and CI match what was built (Tasks 1, 10).
