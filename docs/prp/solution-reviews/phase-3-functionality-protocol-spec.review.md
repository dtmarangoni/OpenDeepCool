# Phase 3 review: functionality and protocol spec

**Review ID:** `phase-3-functionality-protocol-spec`
**Reviewed:** 2026-10-26, at commit `3ec34b7`
**Phase status in the PRD:** complete (2026-10-23), with owner decisions added to the spec until 2026-10-25
**Inputs:** the [Phase 3 plan](../plans/phase-3-functionality-protocol-spec.plan.md) and [report](../reports/phase-3-functionality-protocol-spec.report.md); [`docs/spec/`](../../spec/) (README, protocol, display, music, sensors, settings, parity checklist, `frames/README.md` and the frame files); PRD (Testing Strategy, Open Questions, Decisions Log)
**Overview:** [project-overview.review.md](project-overview.review.md)

## Verdict

The spec is the project's best asset. It's precise enough to reproduce every frame:

- an exact movement procedure;
- a pixel-level bit table;
- every glyph;
- value rules with their boundaries;
- 26 behaviour scenarios.

It labels every fact with its evidence, separates DeepCreative's behaviour from OpenDeepCool's own decisions, and turns both into a test oracle.

Three things weaken it as the ground truth for Phases 5–11:

1. **The oracle generator isn't in the repository** (P3-01, Medium). The generator that draws `docs/spec/frames/` lives in git-ignored `research/`, and every later phase extends it.
2. **Rounding up is defined on real numbers** (P3-03, Medium). In floating point, that gives off-by-one digits.
3. **Small errata** have built up since the sign-off (P3-02, Low).

## Strengths

- **Evidence labels everywhere**, with "unverified" used honestly: for example the meaning of `03 08`, Gpu usage's averaging window, and the equivalence of HWiNFO's and Linux's GPU readings.
- **Device safety is specified, not assumed.** The cooler declares reports 2–5 and an input report, and the spec states that OpenDeepCool never sends them (rule 9). The two messages DeepCreative sends were checked across 159,372 captured messages.
- **DeepCreative quirks are named and explicitly not reproduced**, with the owner's decision attached: the stale paused text, the GPU temperature in mode 18 °F, the 99 caps. This prevents "bug-for-bug parity" from creeping into the tests.
- **"Movement, precisely" is written as an algorithm.** The Rust code and the oracle can then follow the same text independently, which is what makes the scenario tests meaningful.
- **Distinct values per metric** in every matrix case, so a mode that draws the wrong metric fails (rule 11).

## Analysis

### The oracle and its generator

The PRD makes `docs/spec/frames/` the oracle "so Rust output is never compared with Rust output". The frames are text and committed; the program that draws them is not:

- `frames/README.md`: "The files are generated by a local research script from the spec's rules."
- Phases 7, 8 and 9 each start with a task that extends `research/hook/odc_rules.py` and `expected-frames.py` (dash cases, scenario files, spectrum signals, the Dancer).
- Phase 11 Task 8 commits the generators only at the very end, after asking the owner, while deleting the rest of `research/`.

For about six phases the project's ground truth therefore depends on one unversioned copy, on one disk, in a folder that a cleanup task empties. If it's lost, or quietly edited, the expected frames can't be regenerated or reviewed, and a change to the generator leaves no history. It also keeps the generator out of review: nobody but the agent that edits it sees the code that defines "correct".

The generator reads only the spec's rules: the parts that read captures (`render-check.py`'s DeepCreative renderer) are separate. Rule 6 is therefore no obstacle to committing the spec-only parts now.

### Rounding on real numbers

`display.md` Values defines "round up" for usage, temperature and power, and "round to nearest, halves up" for Memory Load. `sensors.md` defines CPU usage as `1 − (idle + iowait) ÷ total`. Implemented in IEEE doubles, as the plans do (`Reading::Value(f64)`, Phase 6), the formula gives:

| Δidle, Δtotal | `(1 − Δidle/Δtotal) × 100` | `ceil` | Exact value |
|---|---|---|---|
| 700, 1000 | 30.000000000000004 | **31** | 30 |
| 42, 100 | 58.00000000000001 | **59** | 58 |
| 57, 100 | 43.00000000000001 | **44** | 43 |
| 99, 100 | 1.0000000000000009 | **2** | 1 |

Reproduced with Python's `float` on 2026-10-26; any IEEE-754 double arithmetic gives the same. The scenario S7 ("99.0 static, 99.01 → `100`") tests the rule at its boundary with literal inputs, so it can't catch this. The error comes from the formula, not from the rule.

The fix belongs in the spec, so both the oracle and Rust follow it: define each displayed number from the integer source.

- **CPU Usage:** ⌈100 · Δbusy / Δtotal⌉ = (100 · Δbusy + Δtotal − 1) div Δtotal, on the integer jiffies.
- **Temperatures:** ⌈m / 1000⌉ on millidegrees.
- **Memory Load:** (200 · used + total) div (2 · total), on kB.
- **Power from µW:** ⌈µW / 10⁶⌉.
- **Power from energy over time:** this is genuinely continuous. State that it is computed from integer µJ and ns, and accept the jitter at boundaries.

### Protocol gaps that matter later

- **Resume from suspend** isn't covered. The spec covers disconnects (the device vanishes and comes back under a new number) but not a resume where the hidraw node survives while the cooler may have lost power. In that case no write fails, so no `03 08` is sent. Whether the cooler needs it is unknown, because its meaning is unverified. See P5-05.
- **One USB ID, possibly several models.** The ID `3633:000c` is "LP-Series", and the manual covers the LP240 too. Whether other LP models share the ID and the 14×14 display is unverified, so the udev rule and the connector would drive them as an LP360. That's worth one sentence in `protocol.md` (see P5-11).

### The parity checklist as the v1 gate

The PRD's key hypothesis is "every item on the parity checklist passes the unattended end-to-end run". Several rows can't pass in that sense:

- **P8:** the cooler blanks about 10 s after frames stop. That's the device's own behaviour, judged by the owner's eye.
- **D28, D31:** DeepCreative-only behaviour, deliberately not reproduced.
- **M10:** DeepCreative's swap, replaced by rule 11.

Phase 11 maps each row "to the test that proved it, or to the owner decision that replaces it". A category column now (proven by a test / replaced by an owner decision / device behaviour, not testable unattended) would make "100 %" well defined before the plans rely on it (see P11-16).

### P3-01: The oracle generator isn't versioned

- **Evidence:** `frames/README.md` (generated by a local research script); the Phase 7, 8 and 9 plans, Task 1 each (extend `odc_rules.py`, `expected-frames.py`); Phase 11 Task 8 (commit them at the end, delete `research/`).
- **Why it matters:** every test of Phases 5–11 compares against files this program writes. The program has no history, no review and one copy.
- **Recommendation:** before Phase 7 extends it, move the spec-only generator to a committed folder (Phase 11 suggests `tools/oracle/`), with the owner's OK. Add a check, in CI or the guard, that regenerating `docs/spec/frames/` changes nothing. Keep the DeepCreative-reading parts in `research/`.

### P3-02: Spec errata

- `display.md` Modes: "`sensors.md` (to come)", though it exists.
- `display.md` Unavailable values: "…drawn as dashes too (owner, 2026-10-24), A reading of 10 000…" (a comma that should end the sentence).
- `frames/README.md`: "every value in full, never capped", while every value is now capped at 9999 (owner, 2026-10-25). The frames don't change, because their readings stay below the cap, but the sentence contradicts `display.md`.
- `parity-checklist.md` Sign-off: "all 73 rows"; the list now has 82. IDs D32–D34 and T5 are gone: they were the Creative rows, removed in commit `41596e0`. Say which rows were added or removed after the sign-off.
- The Phase 3 plan and report still mention Phase 12 and Creative Mode. They're historical records, but a one-line note would stop an agent from following them.
- **Recommendation:** one errata commit with the owner's OK; it touches the spec, so the owner reviews it.

### P3-03: Rounding up on real numbers

- **Evidence:** `display.md` Values; `sensors.md` Driver rules (CPU usage formula); Phase 6 Task 2 (`Reading::Value(f64)`); the table above.
- **Why it matters:** a steady 30 % CPU shows `31%`, and the matrix tests can't notice, because they inject literal values.
- **Recommendation:** define each displayed number in exact integer arithmetic from its source units, as above. Add scenario cases that inject raw counter deltas (for example idle 700 of 1000) rather than finished percentages.
- **Outcome (2026-10-26):** accepted through OV-08. `display.md` Values now defines the integer rules, and checklist row D42 records them. The owner also chose the nearest whole number for every measurement, halves up (checklist D43), so 24 expected °F frames changed. They were regenerated on 2026-10-26 at the owner's request, with the local oracle on exact fractions (`frames/README.md`).

### P3-04: Resume from suspend

- **Evidence:** `protocol.md` Disconnect and reconnect covers vanished devices only.
- **Recommendation:** owner decision. For example, "after every resume, the next write starts a new conversation with `03 08`", with the resume noticed through logind's `PrepareForSleep(false)` signal, plus a scenario. A time gap on the monotonic clock can't detect it, because `CLOCK_MONOTONIC` stops during suspend. See P5-05.
- **Outcome (2026-10-26):** accepted. The owner: when the PC comes back from standby, OpenDeepCool must be back. `protocol.md` has a Standby section (a new conversation with `03 08` after every wake-up, noticed through logind's `PrepareForSleep(false)`), S18 covers it, and checklist P10 records it.

### P3-05: One USB ID for the LP series

- **Evidence:** `protocol.md` Device ("LP-Series"); `docs/hardware/deepcool-lp360.md` (one manual for LP240 and LP360).
- **Recommendation:** note in `protocol.md` that the ID names the series, and that other models are unverified and out of scope (PRD).

### P3-06: Checklist categories

- **Evidence:** PRD Key Hypothesis; `parity-checklist.md` (rows P8, D28, D31, M10); Phase 11 Task 7.
- **Recommendation:** add a column, "How OpenDeepCool satisfies it": test, owner decision, or device behaviour. Phase 11 fills in the test names.

### P3-07: Continuous frames

- **Note:** 10 writes a second, about 640 bytes a second, are needed to keep the picture, so this isn't a cost worth optimising. It's recorded so nobody "optimises" it into a blank display.
